# **1-Technical Overview**

Zakerly is a web-based Learning Management System (LMS) built using ASP.NET Core with a hybrid architecture that combines Clean Architecture and Vertical Slice Architecture. The system exposes RESTful APIs for managing users, courses, lessons, enrollments, assignments, and administrative operations. It is designed to ensure maintainability, scalability, feature isolation, and a clear separation of concerns. PostgreSQL is used as the primary relational database, while JWT Bearer Authentication is used to authenticate users and authorize access to protected resources.

# **2-Architecture Overview**

Zakerly adopts a hybrid architectural approach that combines **Clean Architecture** and **Vertical Slice Architecture**.

Clean Architecture separates the application into independent layers, ensuring that the business logic remains isolated from infrastructure concerns such as databases, authentication, and external services. This approach improves maintainability, testability, and long-term scalability.

Vertical Slice Architecture complements Clean Architecture by organizing the application around business features rather than technical layers. Each feature is implemented as an independent slice containing its own commands, queries, handlers, validators, DTOs, and endpoints. This minimizes coupling between features and allows the development team to work on different modules simultaneously with minimal conflict.

By combining these two architectural styles, Zakerly achieves a modular, scalable, and maintainable codebase while keeping each feature self-contained and easy to evolve over time.

# **3-Architectural Principles**

| **Principle** | **Description** |
| --- | --- |
| Separation of Concerns | Each layer has a single responsibility. |
| Dependency Inversion | Inner layers do not depend on outer layers. |
| Feature Isolation | Every business feature is implemented independently as a Vertical Slice. |
| Single Responsibility | Each class should have one clear responsibility. |
| Dependency Injection | Dependencies are resolved through the built-in ASP.NET Core DI container. |
| Domain-Centric Design | Business rules are implemented inside the Domain layer. |

# **4-Architectural Layers**

| **Project** | **Responsibility** |

# **7-High-Level System Design**

### **Request Flow**

```csharp
Client

↓

ASP.NET Core API

↓

Authentication & Authorization

↓

Vertical Slice (Command / Query)

↓

Application Layer

↓

Domain Layer

↓

Infrastructure

↓

PostgreSQL

↓

Response
```

Every request received by the API is first authenticated and authorized (when required). The request is then routed to the appropriate Vertical Slice, where the corresponding Command or Query Handler processes the business logic. Domain entities enforce business rules, while Infrastructure is responsible for persistence and communication with external services. Finally, the processed result is returned to the client as an HTTP response.

### **Request Lifecycle**

| **Step** | **Description** |
| --- | --- |
| 1 | Client sends HTTP Request |
| 2 | Authentication Middleware validates JWT |
| 3 | Authorization Policy is evaluated |
| 4 | Endpoint receives the request |
| 5 | Validator validates the request model |
| 6 | Command/Query Handler executes business logic |
| 7 | Entity Framework Core accesses PostgreSQL |
| 8 | Response DTO is returned to the client |

# **13- Security Design**

### **Overview**

Security is a fundamental aspect of Zakerly. The system implements authentication, authorization, secure password storage, input validation, and encrypted communication to protect user accounts and application data. Security mechanisms are integrated throughout the application following ASP.NET Core security best practices.

### **Security Mechanisms**

| **Mechanism** | **Description** |
| --- | --- |
| JWT Bearer Authentication | Authenticates API requests using JSON Web Tokens. |
| Role-Based Authorization | Restricts access to endpoints based on user roles (Administrator, Instructor, Student). |
| Password Hashing | User passwords are securely hashed using BCrypt before storage. |
| HTTPS | All communication between clients and the server is encrypted using HTTPS. |
| Input Validation | Incoming requests are validated using FluentValidation to prevent invalid or malicious data. |
| Authorization Policies | Protected resources are accessible only to authenticated users with the required permissions. |

### **Authentication Flow**

```
Client Login

↓

Credentials Validation

↓

Password Verification (BCrypt)

↓

JWT Token Generation

↓

Client Stores Token

↓

Token Sent with Each Protected Request

↓

JWT Validation Middleware

↓

Authorized Request
```

### **User Roles**

| **Role** | **Permissions** |
| --- | --- |
| **Administrator** | Full access to all system resources and management operations. |
| **Instructor** | Manages courses, lessons, assignments, and student submissions. |
| **Student** | Enrolls in courses, accesses learning materials, submits assignments, and views grades. |

### **Security Best Practices**

- Passwords are never stored in plain text.
- Protected endpoints require a valid JWT access token.
- Authorization is enforced through role-based access control.
- All request data is validated before executing business logic.
- Sensitive application secrets are stored in configuration files or environment variables.
- HTTPS secures communication between clients and the server.

# **17- Deployment Architecture**

### **Overview**

The Zakerly system is deployed using a containerized architecture to simplify development, testing, and production deployment. The ASP.NET Core Web API communicates with a PostgreSQL database over a secure internal network, while clients access the application through HTTPS.
